# ADR-001: Гибридная архитектура (Vertical Slice + MVC)

**Статус:** Принято  
**Дата:** Август 2026 г.  

## 1. Контекст и проблема

Изначально для проекта рассматривалась классическая многослойная архитектура (N-layer). Однако по ходу обсуждения выявилась проблема: для добавления одной фичи (например, отмены траты) требовалось вносить изменения в интерфейсы, репозитории, сервисы и контроллеры, разнесённые по разным сборкам. Логика одной операции оказывалась "размазана" по всему решению, что усложняло навигацию и рефакторинг.

В то же время полный переход на строгий Vertical Slice с использованием Minimal API и MediatR был признан избыточным, так как команда предпочитает работать с классическими контроллерами (Controllers) и паттерном Repository.

Дополнительным требованием является изоляция проприетарной бизнес-логики (алгоритмы расчётов, системы подписок) в закрытом ядре (Core), которое не публикуется в open-source.

## 2. Принятое решение

Мы используем **гибридную архитектуру вертикальных срезов (Hybrid Vertical Slice)**. 

Основные правила:
1.  **Группировка по фичам:** Код организован вокруг бизнес-функций (например, `CreateRoom`), а не технических слоёв.
2.  **Классические контроллеры:** Вместо Minimal API используются стандартные классы `ControllerBase`. Каждая фича имеет свой собственный мини-контроллер (обычно с 1-2 методами).
3.  **Сохранение репозиториев:** Работа с БД (SQLite + Dapper) вынесена в отдельный блок, чтобы отделить SQL-запросы от бизнес-логики.
4.  **Никакого MediatR:** Сервисы вызываются напрямую через стандартный Dependency Injection.

## 3. Распределение сервисов и бизнес-логики

Бизнес-логика не дублируется, а распределяется по трём уровням:

*   **Локальные сервисы фич (`Features/{FeatureName}/`):** Узкоспециализированная логика, нужная только для одной операции (например, подготовка DTO перед сохранением).
*   **Общие публичные сервисы (`Features/Common/Services/`):** Переиспользуемая логика (например, конвертация валют, базовые уведомления).
*   **Приватные Enterprise-сервисы (Внешний модуль `Core`):** Здесь инкапсулирована коммерческая ценность продукта. Сюда вынесена сложная математика балансов и механизм централизованной блокировки: единые ключи доступа для комнат, где система может в любой момент отсечь пользователей от функционала при истечении подписки по аналогии с VPN-клиентами. Публичный API взаимодействует с этим слоем исключительно через интерфейсы абстракций.

## 4. Структура директорий

```text
EvenSteven.Api/
├── Features/                     # Бизнес-логика, сгруппированная по фичам
│   ├── Common/                   # Общие интерфейсы и публичные сервисы
│   │   └── Services/
│   │
│   ├── Rooms/
│   │   ├── CreateRoom/
│   │   │   ├── CreateRoomRequest.cs
│   │   │   ├── CreateRoomService.cs
│   │   │   └── CreateRoomController.cs  # Классический контроллер
│   │   └── GetRoom/
│   │       ├── GetRoomResponse.cs
│   │       └── GetRoomController.cs
│   │
│   └── Expenses/
│       └── RevertExpense/
│           ├── RevertExpenseService.cs
│           └── RevertExpenseController.cs
│
├── Infrastructure/               # Техническая реализация
│   ├── Storage/
│   │   ├── SqliteConnectionFactory.cs
│   │   └── Repositories/         # Классические репозитории
│   │       ├── SqliteRoomRepository.cs
│   │       └── SqliteExpenseRepository.cs
│   │
│   ├── Authorization/
│   │   └── RoomAuthMiddleware.cs
│   │
│   └── Middleware/
│       └── GlobalExceptionHandler.cs
│
└── Program.cs
```

## 5. Последствия

*   **Позитивные:** 
    *   Идеальная навигация: разработчик открывает папку фичи и видит всю связанную логику от запроса до контроллера.
    *   Минимум конфликтов слияния (Git merge conflicts) при параллельной разработке.
    *   Простая интеграция закрытого ядра `Core` через DI.
*   **Негативные:** 
    *   Увеличение общего количества файлов в проекте (на каждую фичу создаётся свой контроллер и модель).
    *   Требуется дисциплина, чтобы не превратить общую папку `Common` в свалку несвязанного кода.
